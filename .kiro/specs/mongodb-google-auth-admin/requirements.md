# Requirements Document

## Introduction

The Redemption_App currently keeps the Member_Registry and the Redemption_History in one JSON document on the local filesystem (`DATA_FILE`, default `./data/store.json`), loaded into memory at startup and rewritten atomically on every change. Access is gated by one Shared_Passphrase common to the whole group, and the Redemption_App knows no individual identity: a Session says only "this sender typed the passphrase".

This feature makes three connected changes.

First, persistence moves to a MongoDB deployment reached through a connection URI supplied by the operator. The Member_Registry and the Redemption_History become collections, the single-writer restriction and the "one replica only" caveat of the JSON document disappear, and data already held in the JSON document is imported once so nothing is lost.

Second, the Redemption_App gains real identity through Google sign-in. A person signs in with a Google_Account, the Redemption_App records a User_Account and grants a User_Session, and both survive a restart because they live in the Mongo_Database rather than in process memory.

Third, a new Admin_Page at `/admin` is reachable only by a signed-in person whose User_Account holds the Admin_Role, where the Admin_Role is granted from an operator-configured Admin_Allowlist of email addresses.

The Shared_Passphrase perimeter is retained rather than replaced. It is what keeps a stranger who reaches the port away from the roster, and removing it would either lock the group out or require an approval workflow nobody asked for. A signed-in admin satisfies the perimeter as well, so the owner never types the passphrase; every other Group_Member continues to use it. Requirement 7 states exactly how the two gates combine.

Three behaviours of the JSON document store are deliberately superseded, because a network database cannot honour them: a change is no longer applied to memory before it is durable, a failed write no longer leaves the change visible with a warning, and a failed write no longer reports success. Requirement 2 acceptance criterion 8 and Requirement 3 acceptance criterion 7 state the replacement behaviour.

## Glossary

Terms carried over from the `shared-coupon-redemption` spec keep their meaning there: **Redemption_App**, **Web_Client**, **Redemption_Server**, **Group_Member**, **Hive_ID**, **Member_Label**, **Member_Registry**, **Coupon_Code**, **Redemption_Run**, **Member_Outcome**, **Redemption_History**, **Mock_Mode**, **Shared_Passphrase**, **Access_Gate**.

- **Mongo_Database**: The MongoDB deployment that the Mongo_Connection_URI addresses, holding the Member_Registry, the Redemption_History, the User_Accounts, and the User_Sessions.
- **Mongo_Connection_URI**: The MongoDB connection string, read from the environment, that names the deployment, the credentials, and optionally the database.
- **Mongo_Store**: The Redemption_Server component that reads and writes documents in the Mongo_Database and is the only component that holds a Mongo_Database connection.
- **Store_Document**: The Mongo_Database representation of one domain value, such as one Member_Registry entry or one Redemption_History record.
- **Legacy_Json_Store**: The JSON document at the path held by the `DATA_FILE` environment variable, which held the Member_Registry and the Redemption_History before this feature.
- **Data_Import**: The one-time transfer of Member_Registry entries and Redemption_History records from the Legacy_Json_Store into the Mongo_Database.
- **Identity_Provider**: Google's OAuth 2.0 and OpenID Connect service, which authenticates a Google_Account and issues the Redemption_Server an identity assertion for it.
- **Google_Account**: A Google-operated account that a person authenticates with at the Identity_Provider.
- **Google_Subject**: The Identity_Provider's stable, unique identifier for one Google_Account, supplied as the `sub` claim.
- **User_Account**: The persistent record of one person who has signed in, holding the Google_Subject, the email address, the display name, the Account_Role, and the most recent sign-in timestamp.
- **Account_Role**: The authorization level of a User_Account. The allowed values are `admin` and `member`.
- **Admin_Role**: The Account_Role value `admin`.
- **Member_Role**: The Account_Role value `member`.
- **Admin_Allowlist**: The set of email addresses, read from the environment, whose User_Accounts hold the Admin_Role.
- **User_Session**: The authenticated state the Redemption_Server grants after a successful Google sign-in, bound to one User_Account and recorded in the Mongo_Database.
- **Passphrase_Session**: The Session the Redemption_Server grants after a correct Shared_Passphrase submission, as specified by Requirement 8 of the `shared-coupon-redemption` spec.
- **Sign_In_Flow**: The exchange in which the Redemption_Server sends a person to the Identity_Provider and receives back an identity assertion for a Google_Account.
- **Sign_In_State**: The single-use anti-forgery value the Redemption_Server issues when it starts a Sign_In_Flow and requires back unchanged when that Sign_In_Flow returns.
- **Admin_Page**: The document served at the path `/admin`.
- **Environment_Template**: The tracked file `.env.example`, which documents every environment variable the Redemption_Server reads.

## Requirements

### Requirement 1: Configure the MongoDB connection

**User Story:** As the operator, I want to point the application at my MongoDB deployment with one environment variable, so that the group's data lives in a real database instead of a single file on one machine.

#### Acceptance Criteria

1. WHEN the Redemption_Server starts, THE Redemption_Server SHALL read the Mongo_Connection_URI from the `MONGODB_URI` environment variable, removing leading and trailing whitespace characters from the value, and SHALL read that variable exactly once per process.
2. WHEN the Redemption_Server reads the Mongo_Connection_URI, THE Redemption_Server SHALL determine the database name from the path segment of that URI after removal of leading and trailing whitespace characters, and SHALL use the value of the `MONGODB_DB_NAME` environment variable after removal of leading and trailing whitespace characters when that path segment holds zero characters, and SHALL use the name `sw-code` when both the path segment and `MONGODB_DB_NAME` hold zero characters after removal of leading and trailing whitespace characters.
3. IF the `MONGODB_URI` environment variable is absent or holds zero characters after removal of leading and trailing whitespace characters, THEN THE Redemption_Server SHALL complete startup, SHALL log exactly one warning that names the `MONGODB_URI` variable and states that no Mongo_Database is configured, and SHALL answer every Member_Registry read, every Member_Registry write, every Redemption_History read, and every Redemption_History write with an error message that names the `MONGODB_URI` variable.
4. THE Redemption_Server SHALL hold at most one Mongo_Database connection pool per process, SHALL serve every Member_Registry operation and every Redemption_History operation through that one pool, and SHALL reuse that one pool for the lifetime of the process.
5. IF the Mongo_Store receives no answer from the Mongo_Database within 5 seconds of starting one operation, THEN THE Mongo_Store SHALL abandon that operation at the end of those 5 seconds, SHALL start no further attempt at that operation, and SHALL return an error message that states that the Mongo_Database is unreachable and names neither the Mongo_Connection_URI nor any part of it.
6. THE Redemption_Server SHALL exclude the Mongo_Connection_URI and every part of it, including the credentials and the host it carries, from every response body, from every log entry, and from every value delivered to the Web_Client.
7. WHEN the Mongo_Store opens its connection pool, THE Mongo_Store SHALL create a unique index on the Hive_ID field of the Member_Registry collection and SHALL create an index on the completion timestamp field of the Redemption_History collection, each before the Mongo_Store serves its first Member_Registry operation or Redemption_History operation.
8. IF creating one of the indexes named in acceptance criterion 7 of this requirement fails, THEN THE Mongo_Store SHALL retain every index of that pair whose creation succeeded, SHALL log exactly one warning per failed creation that names the collection and the field of that index, and SHALL serve every subsequent Member_Registry operation and Redemption_History operation.
9. THE Environment_Template SHALL document the `MONGODB_URI` variable and the `MONGODB_DB_NAME` variable, each with its purpose, its default, and the consequence of leaving it unset.
10. IF the `MONGODB_URI` environment variable holds at least one character after removal of leading and trailing whitespace characters and does not parse as a MongoDB connection string, THEN THE Redemption_Server SHALL complete startup, SHALL open no connection pool, SHALL log exactly one warning that names the `MONGODB_URI` variable and states that its value did not parse, and SHALL answer every Member_Registry read, every Member_Registry write, every Redemption_History read, and every Redemption_History write with an error message that names the `MONGODB_URI` variable and that names no part of that value.
11. IF the Mongo_Store establishes no connection to the Mongo_Database within 10 seconds of startup, THEN THE Redemption_Server SHALL complete startup, SHALL log exactly one warning that states that the Mongo_Database is unreachable and names neither the Mongo_Connection_URI nor any part of it, and SHALL answer every Member_Registry operation and every Redemption_History operation received before a connection is established with an error message that states that the Mongo_Database is unreachable.

### Requirement 2: Persist the Member_Registry in MongoDB

**User Story:** As a group organizer, I want the roster stored in MongoDB, so that it survives a restart, a redeploy, and a change of machine without me copying a file around.

#### Acceptance Criteria

1. WHEN a Group_Member submits a Member_Label of 1 to 40 characters and a Hive_ID of 1 to 64 characters after removal of leading and trailing whitespace characters, and the submitted Hive_ID is absent from the Member_Registry collection, and that collection holds at most 99 Store_Documents, THE Mongo_Store SHALL insert exactly one Store_Document holding the whitespace-trimmed Member_Label, the whitespace-trimmed Hive_ID, the enabled state set to enabled, the creation timestamp taken at the moment of that insertion, and a position value greater than the position value of every Store_Document already in that collection, and SHALL return the stored entry holding its identifier, its Member_Label, its Hive_ID, its enabled state, and its creation timestamp.
2. WHEN the Web_Client requests the roster, THE Mongo_Store SHALL return every Member_Registry entry ordered from the lowest position value to the highest position value, so that the order equals the order in which the entries were stored, and SHALL return zero entries together with zero error messages while the Member_Registry collection holds zero Store_Documents.
3. WHEN the Redemption_Server starts, THE Mongo_Store SHALL serve a Member_Registry holding every entry stored before the preceding shutdown, each with the same Member_Label, the same Hive_ID, the same enabled state, the same creation timestamp, and the same relative order as before that shutdown.
4. IF a Group_Member submits a Hive_ID that, after removal of leading and trailing whitespace characters, is character-for-character identical to the Hive_ID of an existing Member_Registry entry, THEN THE Mongo_Store SHALL reject the submission, SHALL insert no Store_Document, SHALL leave the Member_Registry collection unchanged, and SHALL return an error message that names the Member_Label of the conflicting entry.
5. IF a Group_Member submits a new entry while the Member_Registry collection holds 100 or more Store_Documents, THEN THE Mongo_Store SHALL reject the submission, SHALL insert no Store_Document, SHALL leave that collection unchanged, and SHALL return an error message that states the maximum of 100 entries.
6. WHEN a Group_Member confirms removal of a roster entry that is present in the Member_Registry collection, THE Mongo_Store SHALL delete exactly one Store_Document, being the Store_Document of that entry, SHALL omit that entry from every subsequent roster response, SHALL retain the position value of every remaining Store_Document unchanged, and SHALL retain every Redemption_History record that references the deleted Hive_ID with its Member_Outcome unchanged.
7. WHEN a Group_Member changes the enabled state of an existing roster entry to enabled or to disabled, THE Mongo_Store SHALL write the submitted enabled state to the Store_Document of that entry, SHALL leave the Member_Label, the Hive_ID, the creation timestamp, and the position value of that Store_Document unchanged, and SHALL return the updated entry holding its Member_Label, its Hive_ID, and its new enabled state.
8. IF a Member_Registry write does not complete because the Mongo_Database returns no answer within the 5 seconds stated in Requirement 1 acceptance criterion 5 of this document or because the Mongo_Database rejects that write, THEN THE Mongo_Store SHALL leave the Member_Registry collection unchanged, SHALL serve every subsequent roster read from the Mongo_Database without the requested change, and SHALL return an error message that states that the change was not saved and names the attempted change, which supersedes the in-memory-with-warning behaviour of Requirement 1.8 of the `shared-coupon-redemption` spec.
9. WHEN a Member_Registry write completes without failure, THE Redemption_Server SHALL return the affected Member_Registry entry together with zero persistence warning messages.
10. THE Mongo_Store SHALL provide a mapping from a Member_Registry entry to a Store_Document and a mapping from a Store_Document to a Member_Registry entry.
11. FOR ALL Member_Registry entries, mapping the entry to a Store_Document and then mapping that Store_Document back SHALL produce an entry whose identifier, Member_Label, Hive_ID, enabled state, and creation timestamp each equal those of the original entry (round-trip property).
12. IF a Group_Member submits a Member_Label that holds zero characters or more than 40 characters after removal of leading and trailing whitespace characters, or submits a Hive_ID that holds zero characters or more than 64 characters after that removal, THEN THE Mongo_Store SHALL insert no Store_Document, SHALL leave the Member_Registry collection unchanged, and SHALL return an error message that names the rejected field and states the permitted character count of that field.
13. IF a Group_Member submits a removal of a roster entry, or a change of the enabled state of a roster entry, whose Hive_ID is absent from the Member_Registry collection, THEN THE Mongo_Store SHALL leave that collection unchanged and SHALL return an error message that states that the entry is absent from the Member_Registry.
14. IF a roster read does not complete because the Mongo_Database returns no answer within the 5 seconds stated in Requirement 1 acceptance criterion 5 of this document, THEN THE Redemption_Server SHALL return zero Member_Registry entries, SHALL leave the Member_Registry collection unchanged, and SHALL return an error message that states that the roster could not be read.

### Requirement 3: Persist the Redemption_History in MongoDB

**User Story:** As a Group_Member, I want the run history stored in MongoDB, so that what we already redeemed stays readable after a restart and is not capped by what fits in one file.

#### Acceptance Criteria

1. WHEN a Redemption_Run completes, THE Mongo_Store SHALL insert exactly one Redemption_History Store_Document holding the run identifier of 1 to 64 characters, an append counter value, the submitted Coupon_Code of 1 to 64 characters, the completion timestamp, the Mock_Mode state of that Redemption_Run, whether that Redemption_Run stopped early, and one outcome row per enabled Group_Member of that Redemption_Run up to the maximum of 100 outcome rows, each outcome row holding its own Hive_ID, Member_Label, Member_Outcome, response code, and a response message of 0 to 500 characters, retaining the first 500 characters of a longer response message.
2. THE Mongo_Store SHALL assign the first appended Redemption_History Store_Document the append counter value 1, and SHALL assign every subsequently appended Redemption_History Store_Document an append counter value greater than the append counter value of every Redemption_History Store_Document appended before it, including Store_Documents appended before the preceding shutdown, Store_Documents already discarded by the retention rule of acceptance criterion 3 of this requirement, and Store_Documents inserted by a Data_Import.
3. WHEN a Redemption_History Store_Document is appended while the Redemption_History collection holds 200 or more Store_Documents, THE Mongo_Store SHALL delete Store_Documents in ascending order of append counter value, starting with the lowest append counter value, until the collection holds exactly 200 Store_Documents, so that the collection retains the 200 most recently appended records and no record beyond those 200.
4. WHEN the Web_Client requests the history view, THE Mongo_Store SHALL return the retained Redemption_History records, at most 200 records, ordered from the most recent completion timestamp to the oldest completion timestamp, SHALL order records holding the same completion timestamp from the highest append counter value to the lowest append counter value, and SHALL return zero records together with zero error messages while the Redemption_History collection holds zero Store_Documents.
5. WHEN the Redemption_Server is asked for the most recent Redemption_History record holding a given Coupon_Code, THE Mongo_Store SHALL return the retained record whose Coupon_Code is character-for-character identical to the given Coupon_Code and that holds the most recent completion timestamp among such records, SHALL return the record holding the highest append counter value when two or more such records hold that same completion timestamp, and SHALL return no record together with zero error messages when the retained records hold no such Coupon_Code or when the given Coupon_Code holds zero characters.
6. WHEN the Redemption_Server starts, THE Mongo_Store SHALL serve every Redemption_History record retained before the preceding shutdown, each with the same run identifier, the same append counter value, the same Coupon_Code, the same completion timestamp, the same Mock_Mode state, the same early-stop state, and the same outcome rows in the same order as before that shutdown.
7. IF appending a Redemption_History Store_Document fails, THEN THE Redemption_Server SHALL return the Member_Outcomes of the completed Redemption_Run together with exactly one warning message that states that the Redemption_History record was not saved, SHALL leave the Redemption_History collection unchanged with no partially written Store_Document and with every previously retained record intact, SHALL delete no Store_Document under the retention rule of acceptance criterion 3 of this requirement, and SHALL name neither the Mongo_Connection_URI nor any part of it in that warning message.
8. THE Mongo_Store SHALL provide a mapping from a Redemption_History record to a Store_Document and a mapping from a Store_Document to a Redemption_History record.
9. FOR ALL Redemption_History records, mapping the record to a Store_Document and then mapping that Store_Document back SHALL produce a record whose run identifier, append counter value, Coupon_Code, completion timestamp, Mock_Mode state, early-stop state, and outcome rows each equal those of the original record (round-trip property).
10. IF a Redemption_History read fails, or the Mongo_Database returns no answer within the 5 seconds named in acceptance criterion 5 of Requirement 1 of this document, THEN THE Mongo_Store SHALL return zero Redemption_History records together with exactly one error message that states that the Redemption_History could not be read, SHALL withhold every partially read record from the response, and SHALL leave the Redemption_History collection unchanged.
11. IF deleting a Store_Document under the retention rule of acceptance criterion 3 of this requirement fails while the append of that same Redemption_Run succeeded, THEN THE Mongo_Store SHALL retain the appended Store_Document, SHALL log a warning that names the Redemption_History collection and states that the retention rule did not complete, SHALL return the Member_Outcomes of that Redemption_Run together with zero warning messages delivered to the Web_Client, and SHALL apply the retention rule again at the next append.
12. WHEN appending a Redemption_History Store_Document completes without failure, THE Redemption_Server SHALL return the Member_Outcomes of that Redemption_Run together with zero persistence warning messages.

### Requirement 4: Import the existing JSON data once

**User Story:** As the operator, I want the roster and history I already have to appear in MongoDB, so that switching the store does not make me retype 20 Hive IDs.

#### Acceptance Criteria

1. WHEN the Redemption_Server starts while a Data_Import is due, the Redemption_Server holds a Mongo_Database connection, and the Redemption_Server reads and parses the Legacy_Json_Store into the expected shape within 5 seconds of starting that read, THE Redemption_Server SHALL insert one Member_Registry Store_Document per accepted entry of that document, preserving each Member_Label, each Hive_ID, and each enabled state, preserving each creation timestamp the entry holds and using the startup timestamp for each entry that holds none, and assigning position values that place the inserted entries in the relative order they hold in that document, and SHALL insert one Redemption_History Store_Document per accepted record of that document, preserving each Coupon_Code, each completion timestamp, each outcome row, and each append counter value the record holds, assigning append counter values in the relative order the records hold in that document to records that hold none, and SHALL complete every one of these insertions before it answers its first Member_Registry read, Member_Registry write, Redemption_History read, or Redemption_History write, whereby the expected shape is a document that parses into a list of Member_Registry entries and a list of Redemption_History records, each list holding zero or more elements.
2. WHEN the Redemption_Server starts while the Member_Registry collection or the Redemption_History collection holds at least one Store_Document, THE Redemption_Server SHALL insert no Store_Document from the Legacy_Json_Store and SHALL log one line stating that no Data_Import was due, so that a second startup after a completed Data_Import changes neither collection, whereby a Data_Import is due only while both of those collections hold zero Store_Documents.
3. WHEN a Data_Import completes, THE Redemption_Server SHALL log exactly one line stating the number of inserted Member_Registry entries, the number of inserted Redemption_History records, the number of skipped entries, and the number of skipped records, and SHALL leave the Legacy_Json_Store file unchanged in content and in path.
4. IF the Legacy_Json_Store file is absent, cannot be read within 5 seconds of starting that read, or does not parse into the expected shape named in acceptance criterion 1 of this requirement while a Data_Import is due, THEN THE Redemption_Server SHALL complete startup with both collections holding zero Store_Documents, SHALL insert no Store_Document, and SHALL log exactly one warning that names the Legacy_Json_Store path and states which one of these three conditions occurred.
5. IF a Data_Import insertion fails, or a Data_Import has not completed within 30 seconds of its start, THEN THE Redemption_Server SHALL abandon that Data_Import at the end of those 30 seconds or at that failure, SHALL delete every Store_Document that Data_Import inserted, SHALL complete startup, and SHALL log exactly one warning that states that the Data_Import did not complete and that it is retried on the next startup, so that the next startup finds both collections holding zero Store_Documents and finds a Data_Import due.
6. IF deleting a Store_Document inserted by an abandoned Data_Import fails, THEN THE Redemption_Server SHALL complete startup, SHALL log exactly one warning that names the collection holding the retained Store_Documents and states that a Data_Import is no longer due for it, and SHALL answer every subsequent Member_Registry read and Redemption_History read from the Mongo_Database without a further Data_Import attempt.
7. IF an entry of the Legacy_Json_Store holds a Member_Label of zero characters or more than 40 characters after removal of leading and trailing whitespace characters, holds a Hive_ID of zero characters or more than 64 characters after that removal, or holds a Hive_ID character-for-character identical to the Hive_ID of an entry already inserted by that Data_Import, or a record of the Legacy_Json_Store holds a Coupon_Code of zero characters or holds no completion timestamp, THEN THE Redemption_Server SHALL insert no Store_Document for that entry or record, SHALL continue the Data_Import with the remaining entries and records, and SHALL count that entry or record among the skipped counts of acceptance criterion 3 of this requirement.
8. WHEN a Data_Import reads a Legacy_Json_Store holding more than 100 entries or more than 200 records, THE Redemption_Server SHALL insert the first 100 accepted entries in the relative order they hold in that document, SHALL insert the 200 accepted records holding the most recent completion timestamps, and SHALL log one line stating the number of discarded entries and the number of discarded records, so that the Member_Registry collection holds at most 100 Store_Documents and the Redemption_History collection holds at most 200 Store_Documents after that Data_Import.
9. IF the Redemption_Server holds no Mongo_Database connection while a Data_Import is due, THEN THE Redemption_Server SHALL complete startup, SHALL insert no Store_Document, SHALL log exactly one warning that states that the Data_Import was not attempted because no Mongo_Database connection is held and that it is retried on the next startup, and SHALL leave the Legacy_Json_Store file unchanged.

### Requirement 5: Sign in with a Google account

**User Story:** As the owner, I want to sign in with my Google account, so that the application knows who I am without me managing another password.

#### Acceptance Criteria

1. THE Redemption_Server SHALL read at startup the Identity_Provider client identifier from the `GOOGLE_CLIENT_ID` environment variable, the Identity_Provider client secret from the `GOOGLE_CLIENT_SECRET` environment variable, and the public base URL of the deployment from the `APP_BASE_URL` environment variable, SHALL remove leading and trailing whitespace characters from each of the three values, SHALL remove every trailing `/` character from the `APP_BASE_URL` value, and SHALL derive the address a Sign_In_Flow returns to by appending the path a Sign_In_Flow returns to that trimmed `APP_BASE_URL` value.
2. IF the `GOOGLE_CLIENT_ID` variable, the `GOOGLE_CLIENT_SECRET` variable, or the `APP_BASE_URL` variable is absent or holds zero characters after removal of leading and trailing whitespace characters, or the `APP_BASE_URL` value is not an absolute URL naming a scheme and a host, THEN THE Redemption_Server SHALL complete startup, SHALL log exactly one warning during startup that names each such variable and states that Google sign-in is unavailable, SHALL withhold the Google sign-in control from every page, and SHALL answer every request to start a Sign_In_Flow with an error message that states that Google sign-in is not configured and that names none of the three values.
3. WHEN a person activates the Google sign-in control, THE Redemption_Server SHALL issue one Sign_In_State value of 16 to 128 characters that is character-for-character identical to no Sign_In_State value it has issued before, SHALL record that value with an expiry timestamp exactly 10 minutes after the moment of issue, SHALL retain at most 10 unexpired Sign_In_State values per browser and discard the retained value holding the earliest expiry timestamp when an eleventh is issued for that browser, and SHALL direct the person to the Identity_Provider authorization endpoint carrying the Identity_Provider client identifier, the address a Sign_In_Flow returns to, the Sign_In_State value, and a request for the person's email address and display name.
4. WHEN a Sign_In_Flow returns to the Redemption_Server carrying a Sign_In_State value character-for-character identical to a recorded Sign_In_State value that is unconsumed and whose expiry timestamp is later than the moment of that return, an authorization code the Identity_Provider accepts, and an identity assertion holding a Google_Subject of 1 to 255 characters and an email address of 3 to 320 characters, THE Redemption_Server SHALL mark that Sign_In_State value consumed, SHALL store one User_Account keyed on that Google_Subject holding the asserted email address, the asserted display name truncated to its first 100 characters or the asserted email address for an assertion holding no display name, the Account_Role determined by Requirement 6 of this document, and the moment of that return as the most recent sign-in timestamp, SHALL grant one User_Session bound to that User_Account, and SHALL direct the person to the Admin_Page for a User_Account holding the Admin_Role and to the redemption page for a User_Account holding the Member_Role.
5. WHEN a Sign_In_Flow completes for a Google_Subject that already holds a User_Account, THE Redemption_Server SHALL overwrite the email address, the display name, the Account_Role, and the most recent sign-in timestamp of that existing User_Account with the values of that Sign_In_Flow, SHALL leave the Google_Subject of that User_Account unchanged, and SHALL create no second User_Account for that Google_Subject.
6. IF a Sign_In_Flow returns carrying no Sign_In_State value, a Sign_In_State value character-for-character identical to no recorded Sign_In_State value, a Sign_In_State value already consumed, a Sign_In_State value whose expiry timestamp is earlier than the moment of that return, no authorization code, an Identity_Provider error, or an authorization code the Identity_Provider rejects, THEN THE Redemption_Server SHALL grant no User_Session, SHALL create no User_Account, SHALL change no existing User_Account, SHALL deliver no User_Session cookie, and SHALL direct the person to a page holding a message that states that the sign-in did not complete and that names none of the returned values.
7. THE Redemption_Server SHALL record every granted User_Session in the Mongo_Database with the identifier of its User_Account and an expiry timestamp exactly 7 days after the moment of the grant, SHALL accept a User_Session on a subsequent request only while a record for that User_Session is present in the Mongo_Database and the expiry timestamp of that record is later than the moment of that request, and SHALL leave that expiry timestamp unchanged on every request it accepts.
8. WHEN the Redemption_Server grants a User_Session, THE Redemption_Server SHALL deliver it in a cookie carrying the `HttpOnly` attribute, the `Secure` attribute, the `SameSite=Lax` attribute, the path `/`, and a browser-side expiry equal to the expiry timestamp recorded for that User_Session.
9. WHEN a person signs out, THE Redemption_Server SHALL delete any Mongo_Database record present for the User_Session carried by that request, SHALL instruct the browser to remove the User_Session cookie, SHALL return a response that states that the sign-out completed whether or not such a record was present, and SHALL reject every subsequent request carrying that User_Session.
10. THE Redemption_Server SHALL exclude the Identity_Provider client secret from every response body, from every log entry, and from every value delivered to the Web_Client.
11. WHILE a request carries a valid User_Session, THE Web_Client SHALL display, on every page it renders for that request, the email address of the bound User_Account and a sign-out control.
12. THE Environment_Template SHALL document the `GOOGLE_CLIENT_ID` variable, the `GOOGLE_CLIENT_SECRET` variable, and the `APP_BASE_URL` variable, each with its purpose, its expected form, and the consequence of leaving it unset.
13. IF recording a granted User_Session in the Mongo_Database fails, or the Mongo_Database returns no answer within 5 seconds of that recording starting, THEN THE Redemption_Server SHALL grant no User_Session, SHALL deliver no User_Session cookie, SHALL retain the stored User_Account unchanged, and SHALL direct the person to a page holding a message that states that the sign-in did not complete.
14. IF the Identity_Provider returns no answer within 5 seconds of the Redemption_Server sending an authorization code for exchange, THEN THE Redemption_Server SHALL abandon that Sign_In_Flow at the end of those 5 seconds, SHALL grant no User_Session, SHALL create no User_Account, and SHALL direct the person to a page holding a message that states that the sign-in did not complete and that names no Identity_Provider value.
15. IF the identity assertion of a returning Sign_In_Flow holds no Google_Subject of at least 1 character or no email address of at least 3 characters, THEN THE Redemption_Server SHALL grant no User_Session, SHALL create no User_Account, and SHALL direct the person to a page holding a message that states that the Google_Account supplied no usable email address.

### Requirement 6: Restrict the admin page to the admin

**User Story:** As the owner, I want `/admin` open to me and to nobody else, so that the controls I keep there are not reachable by the friends who share the passphrase.

#### Acceptance Criteria

1. THE Redemption_Server SHALL read the Admin_Allowlist at startup from the `ADMIN_EMAILS` environment variable as a list separated by comma characters, SHALL remove leading and trailing whitespace characters from each element, SHALL convert each element to lower case, SHALL discard every element that holds zero characters or more than 254 characters after that removal, SHALL discard every element that holds no commercial at character after that removal, SHALL retain one element per distinct value, and SHALL retain at most the first 50 elements that survive those steps.
2. IF the `ADMIN_EMAILS` environment variable is absent, holds zero characters after removal of leading and trailing whitespace characters, or yields zero surviving elements under acceptance criterion 1 of this requirement, THEN THE Redemption_Server SHALL complete startup with an Admin_Allowlist holding zero elements.
3. WHILE the email address the Identity_Provider asserted in a Sign_In_Flow, with leading and trailing whitespace characters removed and converted to lower case, is an element of the Admin_Allowlist, WHEN the Redemption_Server stores the User_Account of that Sign_In_Flow, THE Redemption_Server SHALL set the Account_Role of that User_Account to the Admin_Role, whether that Sign_In_Flow creates that User_Account or that User_Account already held the Member_Role.
4. WHEN a request for the Admin_Page carries a valid User_Session whose bound User_Account holds the Admin_Role, THE Redemption_Server SHALL serve the Admin_Page.
5. IF a request for the Admin_Page carries no valid User_Session, THEN THE Redemption_Server SHALL withhold every Admin_Page value from the response and SHALL return a response that directs the sender to sign in with a Google_Account.
6. IF a request for the Admin_Page carries a valid User_Session whose bound User_Account holds the Member_Role, THEN THE Redemption_Server SHALL withhold every Admin_Page value from the response and SHALL return an error message that states that the signed-in account is not authorized to reach the Admin_Page.
7. THE Redemption_Server SHALL apply acceptance criteria 4, 5, and 6 of this requirement to every endpoint that serves an Admin_Page value, independently of the route guard of the Admin_Page document, so that a direct call to such an endpoint without a valid User_Session bound to a User_Account holding the Admin_Role returns no Admin_Page value, and SHALL answer such a call to an endpoint other than the Admin_Page document with an error message that states that the caller is not authorized rather than with a response that directs the sender to sign in.
8. WHEN the Redemption_Server decides a request for an Admin_Page value, THE Redemption_Server SHALL read the Account_Role from the Mongo_Database record of the bound User_Account during that request and SHALL use no Account_Role value read during an earlier request, so that an Account_Role written after a User_Session was granted decides that request.
9. WHEN the Redemption_Server starts while the Admin_Allowlist holds zero elements, THE Redemption_Server SHALL complete startup and SHALL log exactly one warning that names the `ADMIN_EMAILS` variable and states that the Admin_Page is reachable by no account, whereby that warning is logged only during startup.
10. WHILE the Admin_Allowlist holds zero elements, THE Redemption_Server SHALL set the Account_Role of every User_Account it stores during a Sign_In_Flow to the Member_Role.
11. WHILE a request carries a valid User_Session whose bound User_Account holds the Admin_Role, THE Web_Client SHALL display a navigation link to the Admin_Page.
12. WHILE a request carries no valid User_Session, carries a valid User_Session whose bound User_Account holds the Member_Role, or carries a valid User_Session whose bound User_Account Account_Role the Redemption_Server could not read, THE Web_Client SHALL withhold the navigation link to the Admin_Page.
13. THE Environment_Template SHALL document the `ADMIN_EMAILS` variable with its separator, its case handling, and the consequence of leaving it unset.
14. WHILE the email address the Identity_Provider asserted in a Sign_In_Flow, with leading and trailing whitespace characters removed and converted to lower case, is absent from the Admin_Allowlist, WHEN the Redemption_Server stores the User_Account of that Sign_In_Flow, THE Redemption_Server SHALL set the Account_Role of that User_Account to the Member_Role, whether that Sign_In_Flow creates that User_Account or that User_Account already held the Admin_Role.
15. IF the Redemption_Server cannot read the Account_Role of the bound User_Account of a request for an Admin_Page value, because the Mongo_Database holds no record for that User_Account or returns no answer within the 5 seconds stated in Requirement 1 acceptance criterion 5 of this document, THEN THE Redemption_Server SHALL withhold every Admin_Page value from the response, SHALL serve no Admin_Page, and SHALL return an error message that states that the authorization of the request could not be determined.

### Requirement 7: Combine the passphrase perimeter with the signed-in identity

**User Story:** As a group organizer, I want the shared passphrase to keep strangers out while the owner gets in with Google alone, so that adding sign-in does not open the roster to the whole internet and does not make me type the passphrase every time.

#### Acceptance Criteria

1. WHERE the Shared_Passphrase environment variable holds at least one character after removal of leading and trailing whitespace characters, THE Access_Gate SHALL admit a request that carries a valid Passphrase_Session, SHALL admit a request that carries a valid User_Session whose bound User_Account holds the Admin_Role in its Mongo_Database record read at the time that request is decided, and SHALL admit no other request except a request whose path is exempt under acceptance criterion 3 of this requirement.
2. WHERE the Shared_Passphrase environment variable holds at least one character after removal of leading and trailing whitespace characters, IF a request whose path is exempt under no part of acceptance criterion 3 of this requirement carries a valid User_Session whose bound User_Account holds the Member_Role and carries no valid Passphrase_Session, THEN THE Access_Gate SHALL reject that request, SHALL withhold every Member_Registry value and every Redemption_History value from the response, SHALL start no Redemption_Run, SHALL retain that User_Session and its Mongo_Database record unchanged, and SHALL return a response that directs the sender to submit the Shared_Passphrase.
3. THE Access_Gate SHALL admit without a Passphrase_Session and without a User_Session every request whose path is the path that starts a Sign_In_Flow, the path a Sign_In_Flow returns to, the path that signs a person out, or the path that accepts a Shared_Passphrase submission.
4. THE Redemption_Server SHALL withhold every Member_Registry value and every Redemption_History value from the response to a request whose path is named in acceptance criterion 3 of this requirement, whether the Access_Gate admitted that request or rejected it.
5. WHERE the Shared_Passphrase environment variable is absent or holds zero characters after removal of leading and trailing whitespace characters, THE Access_Gate SHALL admit every request, and THE Redemption_Server SHALL apply Requirement 6 of this document to every request for the Admin_Page.
6. WHEN a person submits a value that, after removal of leading and trailing whitespace characters from the Shared_Passphrase environment variable value, is character-for-character identical to the Shared_Passphrase, THE Redemption_Server SHALL grant a Passphrase_Session and SHALL grant no User_Session, so that a request carrying that Passphrase_Session alone receives zero Admin_Page values.
7. WHEN a person signs out of a User_Session while carrying a valid Passphrase_Session, THE Redemption_Server SHALL retain that Passphrase_Session, SHALL admit every subsequent request carrying that Passphrase_Session under acceptance criterion 1 of this requirement, and SHALL reject every subsequent request carrying only the ended User_Session.
8. WHERE the Shared_Passphrase environment variable holds at least one character after removal of leading and trailing whitespace characters, IF a request whose path is exempt under no part of acceptance criterion 3 of this requirement carries neither a valid Passphrase_Session nor a valid User_Session, THEN THE Access_Gate SHALL reject that request, SHALL withhold every Member_Registry value and every Redemption_History value from the response, SHALL start no Redemption_Run, and SHALL return a response that directs the sender both to submit the Shared_Passphrase and to sign in with a Google_Account.
9. IF a person submits a value that is not character-for-character identical to the Shared_Passphrase, THEN THE Redemption_Server SHALL grant no Passphrase_Session, SHALL retain every Passphrase_Session and every User_Session the request carries unchanged, SHALL withhold every Member_Registry value and every Redemption_History value from the response, and SHALL return an error message that states that the submitted value did not match and that reproduces no part of the submitted value.
10. WHEN a Passphrase_Session ends while the request carries a valid User_Session, THE Redemption_Server SHALL retain that User_Session and its Mongo_Database record unchanged, SHALL admit every subsequent request carrying that User_Session while its bound User_Account holds the Admin_Role, and SHALL apply acceptance criterion 2 of this requirement to every subsequent request carrying that User_Session while its bound User_Account holds the Member_Role.

### Requirement 8: Show the admin page content

**User Story:** As the owner, I want `/admin` to show me who has signed in and what the store holds, so that the page is worth reaching and I can tell the deployment is wired to the right database.

#### Acceptance Criteria

1. WHILE the Web_Client renders the Admin_Page, THE Web_Client SHALL display the email address of the bound User_Account, the number of Member_Registry entries as an integer from 0 to 100, the number of retained Redemption_History records as an integer from 0 to 200, and the Mock_Mode state as exactly one of the two values enabled and disabled.
2. WHILE the Web_Client renders the Admin_Page, THE Web_Client SHALL display one row for each of at most the 100 User_Accounts holding the most recent sign-in timestamps, each row holding that account's email address, that account's display name, and that account's Account_Role as exactly one of the two values `admin` and `member`, ordered from the most recent sign-in timestamp to the oldest sign-in timestamp, and SHALL order rows holding the same sign-in timestamp from the lowest to the highest email address in case-insensitive character order.
3. WHILE the Web_Client renders the Admin_Page, THE Web_Client SHALL display an indicator holding exactly one of two states, the first stating that the Redemption_Server holds a Mongo_Database connection and the second stating that it holds none, and SHALL display the first state only while the Mongo_Store holds an open Mongo_Database connection pool.
4. THE Redemption_Server SHALL exclude every Hive_ID and every Google_Subject from the Admin_Page response.
5. IF the Mongo_Database returns an error to an Admin_Page read or returns no answer to that read within the 5 seconds stated by Requirement 1 acceptance criterion 5 of this document, THEN THE Web_Client SHALL omit every count that read could not supply, SHALL display in the position of each omitted count a message that states that the Mongo_Database is unreachable, and SHALL display every count and every row supplied by an Admin_Page read that returned an answer.
6. WHILE the Redemption_Server holds a Mongo_Database connection, IF the Mongo_Database returns an error to an Admin_Page read or returns no answer to that read within those 5 seconds, THEN THE Web_Client SHALL display both the indicator of acceptance criterion 3 of this requirement and the message of acceptance criterion 5 of this requirement.
7. IF an Admin_Page read returns zero User_Accounts, THEN THE Web_Client SHALL display zero User_Account rows and SHALL display a message that states that no Google_Account has signed in.
8. IF a User_Account holds a display name of zero characters after removal of leading and trailing whitespace characters, THEN THE Web_Client SHALL display that account's email address in the display name position of that account's row.
9. WHEN the Redemption_Server receives a request for the Admin_Page that it serves under Requirement 6 acceptance criterion 4 of this document, THE Redemption_Server SHALL return every Admin_Page value it read within 5 seconds of receiving that request.
